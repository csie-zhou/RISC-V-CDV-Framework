## 2. Bug 1 — Three Wrong Instruction Encodings

### Where

`tb/tests/riscv_sanity_test.sv` → carried into `tests/test_sanity.py`.

### What was wrong

The original UVM sanity test had three hand-assembled encodings with incorrect field values:

| Instruction | Original encoding | Fixed encoding | Field error |
|---|---|---|---|
| XOR x7, x3, x4 | `0x004183B3` | `0x0041C3B3` | `funct3` bits[14:12] = `001` (SLL) instead of `100` (XOR) |
| SRLI x9, x8, 1 | `0x0014D493` | `0x00145493` | `rs1` bits[19:15] = `01001` (x9) instead of `01000` (x8) |
| SRAI x10, x8, 1 | `0x4014D513` | `0x40145513` | `rs1` bits[19:15] = `01001` (x9) instead of `01000` (x8) |

### How to decode the error

For `XOR x7, x3, x4` (`0x004183B3`):

```
  31      25 24   20 19   15 14 12 11    7 6      0
  0000000   00100   00011   001   00111   0110011
  funct7    rs2=x4  rs1=x3  f3=1  rd=x7  opcode=R
                             ^^^
                          should be 100 (XOR), was 001 (SLL)
```

For `SRLI x9, x8, 1` (`0x0014D493`):

```
  31      20 19   15 14 12 11    7 6      0
  000000000001  01001   101   01001   0010011
  shamt=1       rs1=x9  f3=5  rd=x9   opcode=I
                ^^^^^
             should be 01000 (x8), was 01001 (x9)
```

The SRAI error was identical in structure (same wrong rs1 field).

### Fix

Updated all three encodings in `tests/test_sanity.py:PROGRAM`.

## 3. Bug 2 — UVM Imports in `tb_top.sv`

### Where

`tb_top.sv` lines 1–8 (original).

### What was wrong

```systemverilog
`timescale 1ns/1ps
`include "uvm_macros.svh"      // ← UVM macro package
import uvm_pkg::*;              // ← UVM package — not available under Verilator
import riscv_types_pkg::*;      // ← project SV package — not needed in cocotb branch

module tb_top;
    ...
    initial begin run_test(); end  // ← UVM test launcher
```

Verilator does not ship `uvm_pkg` or `uvm_macros.svh`. The compile would abort immediately with "cannot find file `uvm_macros.svh`."

Also, signals unused by cocotb were left connected (`rvfi_order`, `rvfi_trap`, `rvfi_halt`, `rvfi_intr`, `rvfi_mode`, `rvfi_ixl`) adding unnecessary Verilator lint warnings.

### Fix

Removed all three UVM lines and the `run_test()` block. Unused RVFI signals were either dropped or connected to `()` (open/ignored). The cocotb Python runtime takes over where `run_test()` used to be.

```systemverilog
// BEFORE
`include "uvm_macros.svh"
import uvm_pkg::*;
import riscv_types_pkg::*;
...
initial begin run_test(); end

// AFTER
// (nothing — cocotb drives everything from Python)
```

## 4. Bug 3 — Missing Build System

### What was wrong

No `Makefile` existed on the `cocotb` branch. cocotb requires a `Makefile` that:
1. Sets `SIM`, `TOPLEVEL`, `MODULE`, `TOPLEVEL_LANG`
2. Lists all `VERILOG_SOURCES`
3. Passes Verilator flags (`--trace`, `+define+RVFI`, `+define+SIM`, etc.)
4. Includes `$(shell cocotb-config --makefiles)/Makefile.sim`

### Root cause detail — incomplete VERILOG_SOURCES

The Ibex RTL depends on a large number of `lowrisc_ip` primitive packages that must be compiled in dependency order before the core files. The original `sim/Makefile` on the main branch used a VCS-specific compile script that handled ordering automatically. Translating this to a Verilator `VERILOG_SOURCES` list required manually enumerating all primitives first.

Missing any one package (e.g. `prim_mubi_pkg.sv`, `prim_cipher_pkg.sv`) produces cryptic "undefined type" errors deep inside Ibex files.

### Fix

Created `Makefile` with:
- Full ordered `VERILOG_SOURCES` list (17 primitive packages + 22 Ibex RTL files + `tb_top.sv`)
- `EXTRA_ARGS` including `--trace --assert --timing -Wall -Wno-fatal`
- `+define+RVFI` to enable the RVFI retirement bus inside Ibex
- `+define+SIM` for any simulation-only blocks
- `libisa` target: `gcc -O2 -shared -fPIC -o libisa.so isa_model.c`
- `all: libisa sim` so the C model is always built before the Python testbench runs

## 5. Bug 4 — Missing Python Testbench Layer

### What was wrong

The cocotb branch had no Python testbench at all. The five components needed were:

| File | Role |
|---|---|
| `tb/riscv_types.py` | `RvfiTransaction` dataclass — maps RVFI signal names to Python |
| `tb/riscv_driver.py` | Writes IMEM, asserts/releases reset |
| `tb/riscv_monitor.py` | Watches `rvfi_valid` each cycle, creates `RvfiTransaction`, calls scoreboard |
| `tb/riscv_scoreboard.py` | Steps ISA model, compares `rd_wdata` and `pc_next` per instruction |
| `tb/riscv_env.py` | Constructs driver + monitor + scoreboard, starts monitor coroutine |
| `tests/test_sanity.py` | cocotb test entry point |

### Key design decisions made during creation

**Driver boot address:** Ibex's reset PC is computed as `{boot_addr_i[31:8], 8'h80}`. With `boot_addr_i` unconnected (Verilator defaults to 0), the reset PC is `0x00000080` — word 32 in IMEM. The initial driver therefore wrote the program starting at `imem[32]`:

```python
BOOT_WORD = 0x80 // 4   # 32
for i, word in enumerate(program):
    self.dut.imem[BOOT_WORD + i].value = word
```

**Monitor uses a background coroutine** (`cocotb.start_soon`) that polls `rvfi_valid` on every rising edge, so no test code needs to manually drive the clock — it just waits a fixed cycle budget.

**Scoreboard syncs model PC from RVFI each cycle** to prevent accumulated skew from turning one bug into a cascade of false mismatches.

## 6. Bug 5 — ISA Model Had No Python Interface

### What was wrong

`isa_model/isa_model.c` existed and was correct, but it was only usable via the VCS DPI bridge (`dpi_bridge.c`). There was no way to call it from Python.

### Fix

Created `isa_model/isa_ctypes.py` — a `ctypes` wrapper that:

1. Loads `libisa.so` at runtime from `Path(__file__).parent / "libisa.so"`
2. Mirrors the two C structs (`isa_state_t`, `isa_decoded_t`) as `ctypes.Structure` subclasses
3. Binds `isa_init`, `isa_decode`, `isa_execute`, `isa_rd_reg`, `isa_rd_pc` with correct argtypes/restype
4. Exposes a `step()` method that matches the scoreboard call pattern:

```python
result = model.step(instr, mem_addr, mem_wdata, mem_wmask)
# returns: {"rd", "rd_wdata", "pc_next", "valid"}
```

Store operations are synced into `self._state.mem[]` before `isa_execute` so load instructions that follow a store see the correct data.

## 7. Week 2 Follow-up — ctypes Register Read Unreliable

After the initial bringup was working (scoreboard passing), two reliability issues appeared when the sanity test checked the **final register state**:

### Problem A — `model.reg()` via ctypes was unreliable

The original implementation called `isa_rd_reg()` via ctypes to read back registers for the end-of-test assertion:

```python
# BEFORE (unreliable)
actual = env.scoreboard.model.reg(reg_idx)
```

On macOS/arm64 with Verilator, ctypes occasionally returned stale values for registers that had been written earlier in the simulation. Root cause: `isa_execute` modifies `isa_state_t.regs[]` in C, and the ctypes struct mirror (`self._state`) is not always coherent after repeated `byref()` calls across many simulated instructions.

### Fix A — Python-native register mirror in scoreboard

Added `self.reg_state = [0] * 32` to `RiscvScoreboard`. After every successful `check()` call, the scoreboard writes the RTL-observed value directly:

```python
if t.rd != 0:
    self.model._state.regs[t.rd] = t.rd_wdata   # keep C model in sync
    self.reg_state[t.rd] = t.rd_wdata            # Python mirror for end-of-test reads
```

End-of-test check now reads the Python mirror, bypassing ctypes entirely:

```python
# AFTER (reliable)
actual = env.scoreboard.reg_state[reg_idx]
```

### Fix B — `model.reg()` guard for x0

Also guarded `model.reg()` for index 0 since `isa_rd_reg(state, 0)` could return an uninitialized value on some runs:

```python
def reg(self, idx: int) -> int:
    if idx == 0:
        return 0
    return self._state.regs[idx]   # read struct field directly, not via ctypes call
```

## 8. Bug 6 — IMEM Overflow for Random/Stress Tests

### Symptom

After a manual attempt to fix the sanity test by adding `BOOT_WORD = 0x80 // 4` (32) back to the driver, only `make sanity` passed. `make rand` and `make stress` silently fetched garbage or all-NOP streams.

### Root cause

Ibex's reset PC is hardwired as `{boot_addr_i[31:8], 8'h80}` (see `ibex_if_stage.sv` line 218). With `boot_addr_i` unconnected (Verilator defaults to 0), reset PC is always `0x00000080` — word 32 of IMEM.

The original 256-word IMEM left only 224 usable slots after the 32-word boot offset. `test_rand` generates 1008 words by default; `test_stress` generates ~524. Both overflowed the array, causing out-of-bounds reads that silently returned 0 (illegal instruction) or undefined data in Verilator.

There is a secondary type-compatibility constraint: `test_sanity.py` passes a `list[int]` directly to `load_program()`. The Week 2 driver must accept both `list[InstrItem]` and `list[int]` via a union type with an `isinstance` guard. Replacing the union type with `list[InstrItem]`-only breaks `test_sanity` without changing any other file, violating the spec requirement that `test_sanity` remain a plain directed test.

### Fix — two files

**`tb/riscv_driver.py`** — restored to Week 2 version: union type, loads at `imem[0]`, limit 2048 instead of 256:

```python
async def load_program(self, program: list[InstrItem] | list[int]):
    words = [item.encoding if isinstance(item, InstrItem) else item
             for item in program]
    for i, word in enumerate(words[:2048]):
        self.dut.imem[i].value = word
    for i in range(len(words), 2048):
        self.dut.imem[i].value = NOP
```

**`tb_top.sv`** — increased IMEM to 2048 words and translated the boot offset so driver-loaded index 0 corresponds to PC = 0x80:

```diff
-    logic [31:0] imem [0:255];
+    logic [31:0] imem [0:2047];

-    instr_rdata <= instr_req ? imem[instr_addr[9:2]] : '0;
+    // Subtract boot offset so imem[0] is what Ibex sees at PC=0x80.
+    instr_rdata <= instr_req ? imem[(instr_addr - 32'h80) >> 2] : '0;
```

Address mapping after fix:

| PC | `(PC − 0x80) >> 2` | imem index |
|---|---|---|
| `0x00000080` | 0 | `imem[0]` |
| `0x00000084` | 1 | `imem[1]` |
| `0x00000080 + 4×N` | N | `imem[N]` |

Maximum program size is now 2048 instructions, well above the 1008-word worst case of `test_rand`.
